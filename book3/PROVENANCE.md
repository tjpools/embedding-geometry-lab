# Book Three — Provenance and Versioning

**Status:** Initial version-control gate established August 14, 2026

Book Three enters version control before the dependency graph and chapter spine are re-derived under the closure thesis. The initial baseline must preserve the framing that controls later research and drafting.

## Initial Baseline

The first Book Three commit should include:

- manifests, contracts, structural frames, and cross-book interfaces
- module, dependency, chapter-assignment, and ownership registries
- analytics source, runtime configuration, and tests
- crate descriptions and authorial framing
- the closure-probe contract

The baseline must pass:

```bash
python3 analytics/analyze.py
PYTHONPATH=analytics python3 -m unittest discover -s analytics/tests -p 'test_*.py'
```

The baseline commit must precede chapter-spine re-derivation so that the prior 14-chapter structure and its replacement remain distinguishable in history.

## Attribution Record

Each substantive commit should state the artifact class it changes:

- `frame` — thesis, boundary, ownership, or method
- `structure` — modules, dependencies, chapter derivation, or visual assignment
- `evidence` — source ledger, probe, case, trace, or checksum record
- `manuscript` — chapter or integration prose
- `production` — generated publication output or release tooling

Authorship and public responsibility remain with Terrence J McLaughlin. Transformer collaboration is recorded through attributable conversation-derived artifacts, commit history, inspectable prompts or traces when retained, and the human verification gates in [OWNERSHIP_CONTRACT.md](OWNERSHIP_CONTRACT.md).

## Tracking Policy

Track:

- canonical Markdown and machine-readable registries
- probe and visual generators
- probe fixtures required for reproduction
- tests and build scripts
- final evidence records
- stable reader-facing SVG, PNG, EPUB, or PDF artifacts selected by a manifest

Do not treat caches, virtual environments, temporary exports, editor state, or local credentials as provenance artifacts.

Generated analytics reports may be committed as inspection snapshots, but their authority comes from reproducible generation and tests rather than from their presence in Git. A changed snapshot must be regenerated by the canonical command and reviewed with its source change.

## Checksum Policy

Record SHA-256 values when byte identity is part of the claim:

- canonical visual anchors and their declared exports
- immutable probe packages or fixtures distributed as evidence
- release-candidate EPUB and PDF files
- other artifacts whose exact bytes, rather than only their semantics, must reproduce

Do not checksum ordinary manuscript prose, source code, or analytics JSON merely because it is generated. Git already records source identity, and semantic tests are the stronger contract for structured outputs. A checksum ledger must name the generator, environment assumptions, command, artifact path, and expected digest.

## Change Order

1. commit the validated framing baseline
2. re-derive modules, dependencies, and chapter spine under [CLOSURE_PROBE.md](CLOSURE_PROBE.md)
3. commit the structural replacement separately
4. build chapter briefs, evidence records, and probes
5. add checksum records when stable byte artifacts first exist

This order makes the conceptual transition inspectable instead of folding the old and new architectures into one undifferentiated snapshot.
